## 2. 現行 SKILL.md の構造的課題(再定義の動機)

1. **日本固有性が「日本語ファースト」しかない。** UI Language 以外の軸は汎用 UI レビューであり、skill 名が約束する「日本の非プログラマー向け品質」の実体が薄い。
2. **日本のフォーム入力の観点が皆無。** 氏名・フリガナ、郵便番号・住所、全角/半角、IME、電話番号。日本向け Web で最も事故が多い領域に観点がない。
3. **日本語の組版・表示崩れの観点が皆無。** 長い英単語/URL の折返し破綻、フォント fallback、日付・通貨の表記、`lang` 属性。
4. **a11y が "basics" の一言で具体項目ゼロ。** WCAG 2.2 の観測可能な達成基準にも、日本の法制度の背景にも触れていない。
5. **非プログラマー向け観点が薄い。** 専門用語を説明なしで画面に出さない、エラー文に次の行動を書く、という観点がない。
6. **判定基準が主観的。** "weak hierarchy" 等は判定者依存。観測可能・2値化可能な基準へ寄せる余地が大きい。
7. **強みは「検証の正直さ」。** 未確認を未確認と書かせる報告契約は独自資産であり、維持・強化する。

## 3. 市場と競合(2026-07 調査)

出典は非 GitHub URL と名称のみで記す（公開安全規約 §8）。調査時点: 2026-07-03。

**skill エコシステム**
- SKILL.md 形式は 2025-12 にオープン標準として公開され（agentskills.io）、Anthropic / OpenAI Codex / Google Gemini CLI / GitHub Copilot / Vercel が同一形式を採用。単一の SKILL.md が複数ランタイムで動く状況が確立した。
- Codex は `.agents/skills` / `$HOME/.agents/skills` 等を探索し、`$skillname` 明示呼び出しと description マッチの両方で発火する（developers.openai.com/codex/skills）。
- 配布導線は `npx skills add` ＋公開カタログ skills.sh、Claude Code plugins/marketplace、awesome リストに収斂している。

**競合・類似 skill（UI レビュー/品質/a11y 系の主なもの）**
- frontend-design（Anthropic 公式）: 「AI っぽい平均的 UI」を防ぐ生成時ガイド。生成用でありレビュー用ではない。
- web-design-guidelines（Vercel Labs）: 100+ ルールの汎用レビュー系（コントラスト・フォーカス・ARIA 等）。最有力の汎用競合。
- ui-ux-pro-max ほか網羅型デザイン知識系: 網羅性が強みだがトークン重量級。
- WCAG 2.1/2.2 準拠のレビュー特化 skill、a11y 専門エージェント群: 規格網羅が主眼。

**直接競合・隣接競合・代替手段**（外部レビュー指摘により区別）
- 直接競合（日本語 Web UI 品質ゲート skill）: 調査範囲では未発見（不存在の証明ではない）。日本特化 skill は EC/SEO 領域に少数。日本語技術記事側でも日本語特化 skill は空白領域と指摘されている。
- 隣接競合: 汎用 a11y lint/監査ツール、デジタル庁デザインシステム準拠チェック、日本語 UX 支援 MCP、フォーム生成ツール。これらが日本語対応を強めると差別化が侵食されるリスクがある。
- 代替手段: 人間による目視レビュー、汎用レビュー skill ＋日本人レビュアーの組み合わせ。
- 従って勝ち筋は「日本ドメイン知識の網羅」ではなく、**「日本語 UI の合否を evidence 付きで正直に報告させる契約」**に絞る。ドメイン知識はその判定を可能にする材料として載せる。

**利用者が評価する要素（上位 skill の共通点）**
- description に「何をするか＋いつ発火するか」が具体語で書かれている（明示的な除外条件を含む）。
- ルール/チェック項目数の定量明示と、本文のトークン軽量性の両立。
- progressive disclosure（本文は判定フローに絞り、詳細は参照ファイルへ分離）。SKILL.md 肥大はエコシステム全体の系統的問題として研究でも指摘されている。

## 4. 価値仮説と差別化ポジション

**価値仮説**: エージェントに日本向け Web UI を作らせる/レビューさせる人（特に非プログラマーの発注者・小規模開発者）は、「ビルドが通った＝完成」と報告するエージェントに繰り返し裏切られている。本 skill は (a) 日本語 UI の合否を観測可能な基準で判定させ、(b) 検証したことしか主張させない報告契約で、「日本の利用者に出して恥をかかない UI」への最短経路を提供する。

**差別化ポジション**: 「日本語 UI の合否報告契約」— 生成ガイドではなく、evidence ベースの完了ゲート。

反証条件（この仮説を捨てる/縮小する条件）:
- 汎用上位 skill（web-design-guidelines 等）が日本語組版・日本のフォーム慣行を本格的に取り込んだ場合。
- 利用実績・フィードバックで「日本固有観点よりも汎用観点の精度」が求められると判明した場合。

市場調査を踏まえた実装方針:
1. **「生成ガイド」ではなく「ゲート（合否判定）」であること**を description / README で前面に出す。
2. **SKILL.md 標準の収斂を活かし、複数ランタイムで使えることを README で明確化**する（現行 README の「Codex-style だが他環境でも読める」という記述の具体化であり、公開方針の変更ではない）。
3. **チェック観点数を定量明示**しつつ、本文は判定フローに絞り、詳細チェックリストを `references/checklist.md` へ分離する（progressive disclosure）。`examples/` は「適用例（合成）」に役割を限定する。
4. skills.sh 等のカタログ掲載・マーケットプレイス登録は Non-Goals / gate 対象のため本スコープに含めない（発見可能性は README の記述品質で担保する）。

## 5. 評価軸 v2(日本語 UI 品質基準の再定義)

参照基準（時点情報は本書にのみ記録し、SKILL.md には埋め込まない）:
- WCAG 2.2（W3C 勧告。本 skill は適合宣言・適合試験を行わず、UI レビューで観測可能な達成基準のみ扱う）
- JIS X 8341-3: WCAG 2.2 一致規格への改正が進行中（WAIC が 2025-10 に改正原案作成委員会を発足、2026年度内公示の可能性。確定内容は未公開＝未確認）
- 障害者差別解消法改正（2024-04、合理的配慮の提供が民間事業者にも義務化）。**法令適合の判定には使わない**。アクセシビリティを後回しにしない背景として扱う
- デジタル庁デザインシステム（DADS β v2 系、2026-06 時点 v2.15.0）: 日本語フォーム・エラー表示の参照例。バージョンは SKILL.md に固定しない
- W3C JLReq（日本語組版処理の要件）
- 日本の実測ビューポート分布（2026-05 時点で 414 / 375 / 390 px が上位。実測値は変動するため fallback 候補としてのみ使う）

| 軸 | 内容（観測可能な基準に限定） | 新規/既存 |
| --- | --- | --- |
| A. 日本語 UI コピー品質 | Japanese-first。専門用語を説明なしで放置しない（必要なら短い日本語補足）。エラー文は「何が起きたか＋次に何をするか」。敬体/常体の混在なし。画面に見えるラベルと作業指示の一致 | 既存を強化 |
| B. 日本語の表示・組版 | 長い英単語/URL がはみ出さない・レイアウトを壊さない。`lang="ja"` が設定されている。文字化け・豆腐（表示不能グリフ）がない。日本語本文に不自然な字間・行間がない。日付・通貨・数値が日本語圏の利用者に誤読されない表記（用途に応じ `2026年7月3日` / `2026/07/03` 等） | 新規 |
| C. 日本のフォーム入力 | 郵便番号・電話番号は先頭ゼロが保持される入力型。ハイフン有無・全角/半角・ペースト入力のいずれも受理し正規化（またはエラーで具体的に案内）。フリガナ欄がひらがな/カタカナどちらも受理するか明確に案内。`autocomplete` の意味を壊さない（フリガナ欄に `name` を流用しない等）。分割/単一フィールドはどちらも可とし、実際の入力操作の証拠で判定。生年月日等の遠い日付にブラウザ標準 date picker を安易に使わない | 新規 |
| D. アクセシビリティ（WCAG 2.2 のうち UI レビューで観測可能な最小集合） | ターゲットサイズ 24×24 CSS px 以上（インライン文中リンク・間隔での代替等の例外条件あり）、フォーカスの可視・非遮蔽（Focus Not Obscured）、再入力の強要をしない（Redundant Entry）、ヘルプ/問い合わせ導線の一貫配置（Consistent Help）、コントラスト、キーボード操作、画像の代替テキスト。**適合宣言ではない** | 「basics」を具体化 |
| E. レンダリング検証 | プロジェクトに実測データがあればその上位幅を優先。なければモバイル 375/390/414 のいずれか＋768＋1280 以上を候補にレンダリング確認。状態網羅（empty / loading / error / focus / hover / disabled / 破壊的操作の確認）。横スクロール・タップ困難・折返し破綻の検出 | 既存を強化 |
| F. 正直な報告 | 使用ツール・確認ビューポート・確認した状態・発見と修正・残懸念・`未確認` の明記。検証していない主張の禁止 | 既存の柱を維持 |
| G. 安全・停止条件 | 有料/OAuth/secret/実データ/課金操作は環境ポリシーに従う。auth ループで待たない | 既存を維持 |

設計原則:
- **SKILL.md はトークン効率を守る**: 本文は判定フローと各軸の要点に絞り、詳細チェックリストは `references/checklist.md` に分離する。SKILL.md 単体でも最低限機能する（references が無い環境でも破綻しない）。
- **実装規則ではなく結果基準で書く**: 「単一フィールドにせよ」ではなく「ハイフン有無どちらも受理される」のように、UI の観測結果で判定できる形にする。
- **陳腐化前提の事実（JIS 改正時期、DADS バージョン、ビューポート実測値）は SKILL.md に埋め込まない**。本書と CHANGELOG にのみ時点付きで記録する。
- **実験的 CSS（`text-spacing-trim` / `word-break: auto-phrase` 等）を要求事項にしない**。観測基準（はみ出さない・不自然でない）で判定する。

## 6. 成功指標(無償・バックエンドなしの制約下)

1. skill が壊れない: check:all 3本と CI が常に緑（現状維持）。
2. 実用性の自己検証: 評価軸 v2 の各軸が、悪い合成サンプルで指摘を生み、**十分な品質の合成サンプルを不当に落とさない**こと（false positive の抑制を含む）。
3. 発見可能性: SKILL.md の description と README の When To Use が、日本語 Web UI タスクで確実に発火するトリガー記述として機能すること（除外条件も明記）。
4. GitHub stars / issue 流入は参考指標に留める（能動的な宣伝は本書のスコープ外）。

## 7. 非目標(維持)

- デザインシステム・コンポーネントライブラリ・a11y 認証・法務レビュー・セキュリティ監査ではない。
- WCAG / JIS X 8341-3 の適合試験・適合宣言ツールではない。
- 法令（障害者差別解消法等）適合の判定はしない。
- 実 UI 成果物（デモサイト等）の新設はしない（AGENTS.md §6-④）。
- リリース/タグ発行・パッケージ公開・マーケットプレイス/カタログ登録は人間承認ゲートのまま。
